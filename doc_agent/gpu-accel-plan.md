# GPU 硬件加速计划（tile 解码 → 上屏）

> **定位**：本文件是**计划**（做什么、按什么顺序、每步的出口），不是口径文档。协议/算法硬约束以
> [`gfx-engine.md`](gfx-engine.md) §2 为准，上屏以 [`present-pipeline.md`](present-pipeline.md) 为准，
> CPU 侧的成本结构、优化清单与量测纪律以 [`cpu-accel-plan.md`](cpu-accel-plan.md) 为准。
>
> **取代**：[`gfx-progressive-kernel_old.md`](gfx-progressive-kernel_old.md)（已标记 **old 弃用**：那边的优先级与
> 实现方向被本文件取代——它把"RLGR kernel 并行化"放在第一位，本计划先做 IDWT 且要求**按阶段而不是按
> 相位**搬数据。那边的**约束与实测仍然有效**，作为依据保留。）

## 0. 一句话形状

把 **tile 解码 + 合成**做成**一个 GPU 阶段**：**压缩载荷进、表面/屏幕像素出**；
中间表示（系数、`sign`/`current`、tile 像素）**不跨总线**。

## 1. 目标 / 非目标

目标：

- live 与回放共用同一条 GPU 阶段；`硬件加速` 开关最终要能选"解码+合成的后端"（§7）。
- 判据同 `cpu-accel-plan.md` §0：**每帧计算成本（能耗）为主**，fps 只要够用；正确性门禁是**参考画面**
  （`参考:对比` 的 `bad=0`，两份录像各一套参考，见 `cpu-accel-plan.md` §7）——它对"谁来出像素"中立，
  所以 CPU 线、引擎线、重做后的 GPU 阶段共用同一份参考。

非目标（明确不做）：

- **按相位搬**（只把 IDWT、或只把颜色放 GPU）：中间结果的往返字节 + 每帧固定提交开销会吃掉收益（§3）。
- **只为碎片样本的帧率**做 GPU：那边 CPU 本来就便宜；它跟着受益靠的是"同一阶段摊掉后续项"（§3/§4.3）。
- 不引入新的协议语义或码流分支（§2 的硬约束照旧）。

## 2. 现状基线（同一份整屏录像，每帧，量级）

| 项 | CPU 串行（1 worker） | GPU 引擎（现状） | 说明 |
|---|---|---|---|
| RLGR 位解码 | 几 ms | **百 ms 量级** | 串行/分歧位流，SIMT 最不擅长 |
| 逆 DWT | 一二十 ms（`dec` 内最大项） | 约为 CPU 的两倍 | 见 §4.1：车道分配错，不是任务的错 |
| 颜色 + 合成 | 两项合计一二十 ms | **比 CPU 快数倍** | `rfx_compose` 已按像素并行 |
| 整帧墙钟 | —— | 每帧几百 ms、fps 个位数 | 现状引擎不能进 live |

- 现状引擎慢在 **RLGR（位流分歧）** 与 **IDWT（实现效率）**；颜色+合成这条路已经走通。
- CPU 侧同期的拆相（同一样本）：`idwt` ≈ `dec` 的 4 成半、`state`（系数状态拷贝）≈ 2 成、
  `color` ≈ 1 成半、`rlgr` ≈ 1 成 ⇒ **两侧的最大单项都是 IDWT**，这是先做它的理由。

## 3. 交接成本模型（决定"怎么搬"）

- **固定项**：一次提交 + 等栅栏 ≈ 0.6ms 量级（空提交实测），加每帧 2–3 次 driver 调用。
- **字节项**：host-visible 有效带宽 ≈ 20GB/s 量级（同设备探针：写/拷 19–27GB/s）。
- **按相位搬**（只搬 IDWT，系数往返 24KB/tile）：整屏样本每帧 ms 量级；碎片样本字节量小、但固定项占大头，
  仍是 ms 量级 ⇒ 收益被吃掉一半以上。
- **按阶段搬**（压缩载荷进、像素出）：每帧跨总线的只有**压缩载荷**（每帧百 KB 量级）+ 固定项
  ⇒ 交接退化成一个**与 tile 数无关**的"每帧一次提交"常数。

⇒ **阶段化是形状选择，不是优化项**。它也是"碎片样本同样值得做"的原因：不是靠省那几毫秒 CPU，
而是靠**同一条阶段**把碎片样本的后续项（`state`/`color`/`update` 合成）一起吃掉，且不额外搬字节。

## 4. 各相位的适配性（含并行度分析）

### 4.1 逆 DWT：✓✓（最适合，第一站）

- 工作单元 = (tile, 分量) = 一张 64×64 int16 平面（3 级嵌套：sw = 8/16/32）。
- 每单元 ~10.8k 次逐元素更新（2 遍 × (256+1024+4096)），×3 分量 ≈ 3×10^4 每 tile；
  整帧量级 4×10^7（整屏样本）。每次更新 3–6 条整数运算 + 2–4 读 + 2 写。
- **依赖极浅**：级 3→2→1、每级 X→Y、每遍 even→odd；**同一步内所有点互相独立**（没有递推/前缀依赖），
  临界路径只有"3 级 × 2 遍 × 2 段 = 12 步"。
- **形状**：零分支、零数据依赖、定长循环、工作集 8KB（+ 转置 8KB）⇒ 可全部留在 shared/L1，无分歧。
  ⇒ 可用并行宽度（数千万独立点/步）远超 GPU 宽度：这是**吞吐受限**的活，适合 GPU。
- **现有 kernel（`rfx_idwt.comp`）慢在哪**（`gpuMs idwt` 已量，与 CPU 差 2 倍）：
  1. `local_size_x = 64`，而并行是**按行/列号**分的 —— X 遍只有 8–32 个 lane 有活，
     那条 lifting 链（每次 8–31 次迭代、靠 `X0/H0` 递推）**整条串行在单 lane 里**；
  2. 系数用 **32 位/个** 的 shared 平面（16KB；注释里说这是为了躲 Y 遍写列时的同字 RMW），
     等于把 shared 与车道数一起绑死；
  3. X 遍的 scratch 写入是**读-改-写**（`tmSet` 先读回），每个元素多一次 shared 读；
  4. 每级 2 个 `barrier()`（共 ~8 个/单元），低占用下 barrier 延迟全部暴露；
  5. 单元粒度只有 64 lane ⇒ 常驻 workgroup 数少、单元多波次。
- **设计要点**（改这几条就有现成余量）：
  - 车道铺**样点轴**：每 lane 负责一段样点 + 1 样点 halo，even/odd 段在同一个 lane 内算完
    ⇒ **遍内不需要 barrier**，车道利用率接近满；
  - 转置用 **padded shared**（64×65）避免 bank 冲突；Y 遍同样按样点轴铺；
  - **2×int16 打包**（或每 lane 2 个 int32 元素）做算术，保持与标量逐位等价（截断/移位口径照抄）；
  - **一单元一 workgroup**（或一 tile 三分量一 workgroup），每单元一次装载、一次回写。
- 出口口径：`参考:对比 bad=0` + `gpuMs idwt` 落到 **ms 量级**（CPU 侧同项一二十 ms）；碎片样本一并记录。

### 4.2 颜色 + 合成：✓（已有实现可复用）

`rfx_compose` 已按像素并行、且已在 GPU 上比 CPU 快数倍 ⇒ 保留其形态，随阶段一起走。

### 4.3 `state`（`sign`/`current`）与 `update`（tile→surface）：在阶段内**消失/变身**

CPU 侧这两项是"把系数/像素搬到别处"的成本（`state` 每 tile 约 50KB 读写、`update` 是 tile→surface 拷贝）。
在 GPU 阶段里：持久状态留在 device 缓冲、合成就是 `rfx_compose` 写表面 ⇒ **不需要各自的搬运**。
这正是碎片样本能跟着受益的原因（§3）。

### 4.4 RLGR：✗ 现状形态（唯一需要改算法的地方）

- 一条 stream 是**串行、数据依赖、分歧**的位流（一条 stream 只有几十个符号却要展开 4096 个系数）；
  现状 GPU 比 CPU 贵一个量级。
- 方向与实现约束见 old 文档 §2（producer/consumer：lane 0 跑状态机、其余 lane 并行量产；barrier 纪律、
  补零尾终止条件、奇下标整字覆盖、队列容量、先在 host 侧对拍）——**那些约束仍然有效**。
- **在它做成之前，整段阶段化没有意义**（瓶颈会留在 RLGR），所以排在 M3。

### 4.5 upgrade / restamp（type 2/3）：待量

逐系数细化、分歧中等；CPU 侧现状只占 `dec` 的百分之几到半成 ⇒ **先留在 CPU**，除非 §2 的账变了。

## 5. 里程碑（每步都要有可量出口）

| 里程碑 | 内容 | 出口（量到的数） |
|---|---|---|
| **M0** | 交接微基准：同一帧的系数按三种口径跑（staging 拷贝 / 持久映射 + 刷脏范围 + 栅栏 / 只单向），并给"每帧、每消息 host 侧开销"记账 | `emptySubmit`、每帧固定项、字节斜率三个实测数 |
| **M1** | **IDWT kernel v2**（§4.1 的设计要点） | `gpuMs idwt` 落到 ms 量级 + 两份录像 `参考:对比 bad=0` |
| **M2** | **阶段化**：载荷上、像素下，整帧一次提交/一组栅栏，中间表示不落地 | `syncDrain`/`emptySubmit`、每帧 host 侧开销、`presentSplit` |
| **M3** | **RLGR**（producer/consumer，约束照 old 文档 §2.2） | `gpuMs rlgr` + `参考:对比 bad=0` |
| **M4** | **live 接管**：引擎进 live 会话；开关与回退口径见 §7 | live 的 `本机`/duty/帧墙钟 + 与同码流回放的逐相对照 |

- M1/M2 在**回放路线**上就能量完，不依赖 live 接管；CPU 侧（§6）并行推进、互不阻塞。引擎路线（`GfxReplayRoute::kVulkan*`）已从 dev 页撤下、只从代码跑得到：重做期间它就是 M1–M3 的实验台。

## 6. 同时推进的 CPU 侧（另一条线，两端共享收益）

- 顺序：**逆 DWT 向量化**（最大项）→ `state` 流量与 `color` 的向量化 → `update` 的掩码拷贝 → RLGR 最后；
  多核/平台适配排在这一切之后（`cpu-accel-plan.md` §6 的"阶段一 → 阶段二"）。
- ⚠ **门禁是同一份参考画面**：CPU 侧改动必须**逐位等价**才能继续用旧参考（`cpu-accel-plan.md` §7）；
  引擎/GPU 侧只要像素与参考一致即通过——与实现无关。
- 细节与量测纪律见 [`cpu-accel-plan.md`](cpu-accel-plan.md) §3/§6/§7。

## 7. 开关与回退口径

- 现在的「硬件加速」= **上屏后端**（Vulkan / GLES），按**呈现判定**置灰，判据与 Vulkan 面见
  [`native-libraries.md`](native-libraries.md) §6。
- 引擎进 live 后需要**第二个开关**（解码后端）+ "引擎初始化失败 ⇒ 回退 gdi"的口径；
  **不要**把它与上屏那个复用同一个设置项（见 [`gfx-engine.md`](gfx-engine.md) §7）。
- 模拟器不参与 GPU 路径（其 Vulkan 实现会按标准接口谎报能力）。

## 8. 别重犯（已否证）

- 用"跳过某条 dispatch + 差值反推"做归因（用 timestamp query）；**每 tile 计时**（本平台时钟贵，
  要量就用 1/16 采样，见 [`cpu-accel-plan.md`](cpu-accel-plan.md) §7）。
- 把 payload 整段搬进 shared；32bit 字缓存；跨消息合并 decode（与 restamp 时序互斥）。
- 用"逐条矩形"做 GPU 侧脏区（见 [`present-pipeline.md`](present-pipeline.md) §4.3）。
- **按相位搬中间结果**（§3 的结论）。
