**CPU 路线** = FreeRDP gdi 解码 + 我们自己的呈现器。

## 0. 起点：阶段一留下的基线

阶段一（通用单核优化）落地了三件：抽取支逆 DWT 的**逐位等价**改写、`-DWITH_SIMD=ON`（FreeRDP 自己的
NEON：抽取支 DWT / 量化移位 / `yCbCrToRGB`）、以及"RLGR 直写 `sign`、去量化改成 `sign → buffer`"——
把每 tile/分量的那趟 8KB 搬运整趟删掉。相对起点，整屏样本上 `idwt`/`color`/`state` 各降 2~6 成，
`本机` 与整轮 `cpu=` 各降三成以上（两份录像都过门禁）。计划里的第四件（`update` 的掩码拷贝向量化）
实测**中性**、已撤回；理由与两次"写窄循环但没收益"的教训见 [`gfx-engine.md`](gfx-engine.md) §8.5。

- **现状**：解码 worker 数**固定为 1**（`hmrdp_decode_tuning.cpp` 的 `kPinnedWorkers`）⇒ 有一条干净的
  单核基线；设置页的「解码线程数」与回放页的「线程」因此**置灰**（存的值保留，重新开放只需把
  `kPinnedWorkers` 改回 0 并去掉两处置灰）。
- **入口条件**：阶段一的基线在上面（否则"并行快了"分不清是算法还是调度）。
- **在 M-a 之前不要**再调 `kPinnedWorkers`/fan-out——那只是把同一个问题换个位置暴露（§1）。

## 1. 现在这套并行：为什么不能用

唯一可用的并行度旋钮是 **tile 解码的 worker 数**（WinPR 线程池，每个 codec 一个池；本平台**不能绑核/
绑簇**）。控制面：patch 导出的 `HmrdpSetDecodeThreads/Get/Apply`，app 侧 `hmrdp_decode_tuning.*`，
设置页「解码线程数」（0=自动 / 1..8），dev 回放页有「线程」；**`n == 1` 走完全串行分支**（不建池、
不提交、不唤醒、不等待）。自动值 = `min(性能核数或核数, 4)`。

标定结果（同一样本内比较；这是"打开旋钮时的知识"，当前旋钮是钉住的）：

| worker | 墙钟（`本机`/帧） | 整轮进程 CPU |
|---|---|---|
| 1（串行） | 整屏样本 2× 出头（fps 约 0.5×）；碎片样本接近（+4% 量级） | **最低**（整屏约 35%，碎片约 45%） |
| 2 | 已到并行平台 | 平台值 |
| 4（自动） | 与 2/6/8 相同 | 平台值 |
| 6 / 8 | 不再下降 | 不再变化 |

- **≥2 之后墙钟完全不涨**：串行→2 的跳变已超过 2x，2→8 又不涨 ⇒ **每个 tile 的有效成本随并发度变化**，
  不是"把工作平均切开"。机制是**并发下的访存/缓存干扰** ⇒ **调 worker 数是把问题换个位置暴露，不是解**。
- **并行买到的墙钟远少于核数**：整屏样本 4 个 worker 只把 tile 解码段压到串行的三分之一量级（`dec`），
  而"解码之外的线程 CPU"是那段墙钟的**十倍量级** ⇒ 池里大部分 CPU 花在争用/空转（分片投递的共享计数
  自旋）而不是解码。**这是"现在这套池"的问题，不是"并行"的问题**——所以要做的是换池/换任务队列（§2），
  而不是把 worker 数调来调去。
- ⚠ **两轮的频率档不同，别把 CPU 秒数直接当能量**：多核一起跑时 SoC 会把档压低，单核那轮能拿到的最高档
  明显更高（读法见 [`gfx-engine.md`](gfx-engine.md) §8.1）⇒ 上面两轮的 `cpu=` 不能横向读成"并行多烧了
  N 倍电"。
- 已否定：池 fan-out 4→8（`dec`/`本机` 都没有收益）——**在现有池实现下**已到头；换池/换任务队列要重开
  这条打分（§2）。
- **这套池的"放大倍数"**（同一会话、同一录像、`mode=fast`，相对单核）：整轮进程 CPU 涨到约 **3 倍**，
  其中解码段本身约 **4.6 倍**；而帧墙钟只降 **1.5 倍**。请求 2 / 4 / 8 个 worker 得到的进程 CPU、
  池段墙钟与帧墙钟**完全一样**，池自己的账（各 chunk 回调忙时间之和 ÷ 池段墙钟）给出的有效并行宽度
  远高于请求值 ⇒ **请求的 worker 数没有变成有效并行宽度**，多出来的 CPU 是池自身的损耗。
  - 线程账佐证：单核那轮全部解码在**一个线程**里（其余线程几乎不耗 CPU）；并行那轮接收线程只剩
    parse/update/present，而进程 CPU 几乎全部记在 worker 上 ⇒ 损耗是**真烧 CPU**，不是"在等"。
  - 按能量口径（每核 busy×f²，§2）读，各档在重复噪声内**持平**：并行把"一核高频"换成"多核低频"，
    总账不省也不多。⇒ 这条线的收益只能来自**换掉这套池**，不能来自调线程数。

## 2. 里程碑

**目标**：把"多核低频"这条能效路线做对——它本身是正当手段，要做的是**换掉现在这套并行**，而不是回避并行。

| # | 项 | 做法要点 | 门禁/出口 |
|---|---|---|---|
| **M-a** | **换池/换任务队列**：`ffrt`（提交任务、由系统决定何时/在哪跑）或等价的平台队列，按 [`native-libraries.md`](native-libraries.md) §6 的 Capability 模式探测 + 降级；保留 WinPR 池作兜底 | 不能碰：**同一个 tile 仍由单个 callback 独占解码**（否则参考对比失去意义）；出口：同一档下的 `dec`/`本机`/`cpu=` |
| **M-b** | **producer/consumer 流水线**：worker 解码 region k 时，RDP 线程解析 k+1 / 合成 k−1，把现在"每条 region 一次 fork/join + 解析/`update` 全在 RDP 线程"的串行段藏起来 | ⚠ 合成的顺序语义（同帧重复合成、clip 取 REGION 头）见 [`gfx-engine.md`](gfx-engine.md) §2.2；出口同上 |
| **M-c** | **worker 数按 duty 自适应**：到达侧限速（duty 低）时回落 1，受限时用 2–4；判据用已有的到达间隔/duty 加滞回，旋钮与热切换早就有 | 出口：同一录像的 duty↔worker 曲线；`cpu=` 按档位换算 |

- **顺序**：M-a 先（池/调度是另外两项的地基）。M-a 之前不要动旋钮；M-b/M-c 的收益都要在 M-a 之后量，
  否则分不清是"池换好了"还是"worker 数变了"。
- **出口一律按"同档 CPU 时间"或 duty 下的功耗读**：多核与单核跑在不同频率档是常态，`cpu=` 秒数不能直接
  比。每项先有自己的基线（同一录像、同一 `cpuKHz=` 档）再 A/B；正确性门禁仍是两份录像的参考对比。
- **量测照 [`gfx-engine.md`](gfx-engine.md) §8.3 的纪律**：多轮一律走 `native/scripts/replay-rounds.ps1`，
  等**这一轮**的 `state=finished` 再动下一步，不要按内容猜；A/B 纯 CPU 侧的改动要用 CPU 受限的样本。
